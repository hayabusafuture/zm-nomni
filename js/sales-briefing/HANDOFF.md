# Sales briefing ("At a glance"): developer handoff

The "At a glance" box at the top of the dashboard's Sales tab is generated by `sales-briefing.js`. This note covers what production data it needs, what the prototype fakes, and what is left to build. For how the module works (input shape, rules, tuning), see [README.md](README.md) and the comment at the top of `sales-briefing.js`.

## It can run in production as is

- **No AI and no network.** It's plain arithmetic and fixed sentence templates, with no `fetch`, no external calls and no `Math.random`. Wording is picked from a hash of the input, so the same data always gives the same text.
- **Cheap.** It runs in milliseconds, in the browser or on a server. There's no per-call cost.
- **Nothing is invented.** Every number it states comes from its input. The only links it draws between facts are arithmetic (see README).

The work is upstream: getting real POS data into the input shape.

## Where each input comes from in real data

| Briefing input | Source in POS data | Risk |
|---|---|---|
| `revenue` (current, previous) | Invoice totals for the scope and period | Low |
| `channels[].revenue`, `previousRevenue` | Invoice totals grouped by **order type** | Low, if order type is recorded on every invoice |
| `channels[]` dine-in `covers`, `previousCovers` | **Guest count** entered on each dine-in bill | **Highest.** Staff often skip it or leave it at 1. |
| `channels[]` off-premise `orders`, `previousOrders` | Count of invoices per order type (1 per order) | Low |
| `outlets[]` revenue and dine-in revenue | Invoice totals by outlet, and by outlet × order type | Low |
| `outlets[]` `covers`, `previousCovers` | Dine-in guest count by outlet | Same as dine-in covers |
| `items[]` revenue, times sold, rank | Invoice lines, matched by **product ID** | Low |
| `daily` dine-in covers | Dine-in guest count per outlet-local trading day | Same as dine-in covers |
| `heatmap` | Invoice timestamps converted to outlet-local time | Low (`buildHeatmapGrid` in `js/heatmap-summary/` already does it) |

### Confirm first

**Does the Nomni POS integration give Procure an order type and a guest count on each invoice?**

- **Both present and reliable:** everything above works.
- **Guest count missing or unreliable:** don't pass dine-in `covers`, `previousCovers` or the per-outlet `covers`, and omit `daily`. The briefing still works from revenue, outlets, channel share, items and the heatmap. It loses the "more dine-in guests / higher spend per head" breakdown, the per-outlet dine-in spend per head finding and the "yesterday" finding.
- **Order type missing:** there's no channel breakdown at all, and the Sales by channel panel has the same problem.

## What the prototype fakes (don't copy this into production)

`buildSalesBriefingInput()` in `Procure - Dashboard.html` builds the input from the prototype's panel data. Several figures there are not real, only stand-ins:

| Prototype stand-in | Production replacement |
|---|---|
| `channelVolumes()` splits the Covers panel total into dine-in covers and off-premise orders, using a fixed "value per unit" for each channel plus a small seeded shift | Real guest counts and invoice counts per order type |
| Channel revenue for any period = period revenue × channel share (the Sales by channel panel only holds this month) | Real channel revenue for both periods |
| Item previous figures = current ÷ the ratio of the item's last two complete months (Top items only holds one period) | Real item revenue and times sold for the previous period |
| Daily dine-in covers = the Covers chart × the mock dine-in share | Real daily dine-in guest counts |
| `today: '2026-09-22'`, and the last day in the data is treated as the last closed day | The actual date, and `lastClosedIndex` = the last fully synced trading day, never today |

## What to build

1. **One shared normaliser** feeding both the Sales panels and the briefing, so they can never disagree. The README's "Before shipping" table lists what it must handle: dine-in-only covers, outlet-local time, excluding refunds and deleted invoices, like-for-like weekdays, excluding outlets that connected POS mid-period, matching items by product ID, and closed days only.
2. **Previous-period queries** for channels and items, which the prototype panels don't have.
3. **Per-user storage for `memory`** (browser storage or server). Pass back whatever the last call returned. It only controls which supporting findings rotate; without it the text is still correct.
4. **Dine-in-only Covers and Spend per head panels.** In the prototype, the Covers total counts dine-in covers plus off-premise orders together. See the README note on why the panels should be dine-in only.

## How the dashboard uses it

- **Placement:** first element inside the Sales tab panel, so it only shows on that tab and hides with the rest of the tab for an outlet without POS.
- **Re-rendered** on every scope, period or data-set change.
- **`coverage` is not passed.** The summary cards already show POS coverage ("9 of 10 outlets"), so the briefing doesn't repeat it.
- **Two-line clamp:** a "View all" / "Show less" button, with `aria-expanded`, shows only when the text overflows two lines. The fit is re-checked after each render, on window resize, and when the box's width changes. New text always starts collapsed. The full text is always in the page, so screen readers read all of it.
- **Shimmer:** for 0.65 s whenever the text changes, with `aria-busy` set on the box during it. The briefing isn't actually loading anything; this is purely a visual transition carried over from the old AI briefing. Drop it if the real call is synchronous and the effect isn't wanted.

## Known issue in the module

When off-premise orders and average order value move in opposite directions, the revenue sentence names both halves of the same number. For example:

> …mostly from more takeaway and delivery orders (+3%, with average order −4%). Smaller takeaway and delivery orders pulled the other way (−4%, with orders +3%).

The "pulled the other way" clause should skip the part that shares a channel group with the lead contributor. It shows up often with the prototype's mock data; real data may trigger it less often, but it should be fixed, with a test, before shipping.
